## 1. Why This Document Exists

The official brief states:

> "Write this section before you begin training and commit it to your repository before your first Kaggle run. Define the complete set of metrics and conditions you will use to determine whether your pod is trustworthy enough to connect to the orchestrator."

This design document is that commitment, written in advance of any training. Every threshold value listed here is either (a) a **placeholder awaiting research**, or (b) a **researched value with justification**. The evaluators will compare actual results against these commitments.

**Golden rule**: No threshold may be changed after the first training run begins. If results fall short, the gap is reported honestly — the threshold is not retroactively relaxed.

## 2. Files in the `eval/` Directory

The eval suite consists of **two files** that must exist in the repository before training:

| File | Purpose | Committed Before Training? |

## 3. Input to the Eval Suite

### 3.1 Source File

```
results/orchestrator_outputs.jsonl
```

This file is generated by `src/run_eval.py` (the end-to-end evaluation pipeline). It contains one JSON object per line — one per market snapshot in the evaluation window.

### 3.2 Evaluation Window

- **Days 31–60** of `market_states.parquet`
- Evaluated in **5-day rolling blocks**: days 31–35, 36–40, 41–45, 46–50, 51–55, 56–60
- **k-fold cross-validation is disqualifying** — the brief forbids it

### 3.3 Per-Row JSON Schema

Every line in `orchestrator_outputs.jsonl` must contain the following fields:

```json
{
  "day": 31,
  "timestamp": "2024-10-01T09:15:00+05:30",
  "actual_direction": "PE",
  "predicted_direction": "NEUTRAL",
  "conviction": 0.0,
  "schema_valid": true,
  "reason_code": "ADX_SUPPRESSED",
  "vix": 26.8,
  "adx": 14.2
}
```

#### Field Definitions

| Field | Type | Source | Description |
|-------|------|--------|-------------|
| `day` | int | `market_states.parquet` | Trading day number (31–60) |
| `timestamp` | str ISO | `market_states.parquet` | Exact snapshot timestamp |
| `actual_direction` | str | Parquet `label` column | Ground truth: `CE`, `PE`, or `NEUTRAL` |
| `predicted_direction` | str | Orchestrator output | Final direction after all 3 rules |
| `conviction` | float | Orchestrator output | Conviction score (0.0–1.0). Preserved even if downgraded to NEUTRAL |
| `schema_valid` | bool | Derived | `true` if `reason_code != "PARSE_FAILURE"`, else `false` |
| `reason_code` | str | Orchestrator | One of: `ADX_SUPPRESSED`, `PARSE_FAILURE`, `LOW_CONVICTION`, `PASSED` |
| `vix` | float | `market_states.parquet` | India VIX at snapshot |
| `adx` | float | `market_states.parquet` | ADX at snapshot (for verifying suppression logic) |

**Important**: The eval suite **never sees the raw model output**. It only sees what the orchestrator emitted downstream. This mirrors production: the downstream pipeline reads orchestrator output only.

## 4. `eval/thresholds.py` — Threshold Dictionary

### 4.1 Purpose

Centralise every numerical threshold that constitutes "pass" or "fail" for the pod. By isolating thresholds in one file, we make the commitment explicit and auditable.

### 4.2 Structure

A single dictionary named `THRESHOLDS` with string keys and float (or None) values.

### 4.3 Required Keys

| Key | What It Controls | Initial Value | Research Required? |
|-----|-----------------|-------------|-------------------|
| `min_directional_accuracy` | Minimum acceptable accuracy in any 5-day window | `None` | **Yes** — what edge is realistic for NIFTY options? |
| `fail_directional_accuracy` | Hard fail: if any window falls below this, pod is rejected | `None` | **Yes** — below random baseline? |
| `min_schema_pass_rate` | Minimum % of outputs that are valid JSON | `None` | **Yes** — production systems need extremely high validity |
| `max_ece` | Maximum Expected Calibration Error for conviction scores | `None` | **Yes** — what ECE indicates a well-calibrated text-generated score? |
| `max_parse_failure_rate` | Maximum acceptable % of parse failures | `None` | **Yes** — any parse failure is a liability |
| `min_high_vix_accuracy` | Minimum accuracy in high-VIX windows | `None` | **Yes** — must not collapse under stress |
| `max_vix_accuracy_gap` | Maximum allowed gap between low-VIX and high-VIX accuracy | `None` | **Yes** — model must be regime-robust |

### 4.4 Accessor Functions

| Function | Signature | Behaviour |
|----------|-----------|-----------|
| `get_threshold(key)` | `str -> float` | Returns the threshold value. Raises `ValueError` if the value is still `None` (unresearched). |
| `all_thresholds_set()` | `() -> bool` | Returns `True` if every key in `THRESHOLDS` has a non-None value. |
| `missing_thresholds()` | `() -> list[str]` | Returns a list of keys that are still `None`. |

### 4.5 Why Placeholders Are Acceptable (Temporarily)

The brief says to commit the eval suite **before training**. It does not require every threshold to be filled on Day 1. However, **training must not begin until thresholds are set**. The `get_threshold()` function enforces this by raising if a value is missing.

**User responsibility**: Research and fill these values based on:
- Academic literature on NIFTY options directional accuracy
- Baseline random-walk accuracy (~50%)
- Your own exploratory data analysis of the training window
- The specific risk tolerance of a systematic trading system

**I (Claude) will never invent threshold numbers.** I will only scaffold the structure and remind you when values are missing.

## 5. `eval/eval_suite.py` — Metric Functions

This file contains one function per metric, plus a master orchestrator function that runs them all and prints a report.

### 5.1 `load_results(filepath) -> pd.DataFrame`

**Purpose**: Read the orchestrator output JSONL into a pandas DataFrame.

**Parameters**:
- `filepath`: `str` or `Path` — path to `orchestrator_outputs.jsonl`

**Returns**:
- `pd.DataFrame` with one row per record

**Error Handling**:
- Raises `FileNotFoundError` if file does not exist
- Warns (but does not crash) on lines that fail JSON parsing — skips them and continues
- Raises `ValueError` if no valid records are found

**Implementation Notes**:
- Uses the standard library `json` module, not `jsonlines`, to avoid extra dependencies in the eval suite
- Parses line-by-line with `json.loads()` inside a `for` loop
- Handles UTF-8 encoding explicitly

---

### 5.2 `wilson_score_interval(k, n, alpha=0.05) -> (float, float)`

**Purpose**: Compute the Wilson score confidence interval for a proportion. This is the statistically correct way to put error bars on accuracy estimates, especially when `n` is small or accuracy is near 0 or 1.

**Parameters**:
- `k`: `int` — number of successes (correct predictions)
- `n`: `int` — total number of trials (predictions in window)
- `alpha`: `float` — significance level. Default `0.05` for a 95% confidence interval.

**Returns**:
- `(ci_low, ci_high)` — two floats in `[0.0, 1.0]`

**Formula** (for reference):

```
p = k / n
z = Φ⁻¹(1 - α/2)
denom = 1 + z² / n
centre = (p + z² / (2n)) / denom
margin = z × √(p(1-p)/n + z²/(4n²)) / denom

CI = [max(0, centre - margin), min(1, centre + margin)]
```

**Edge Cases**:
- If `n == 0`: returns `(0.0, 1.0)` (uninformative interval)
- If `k == 0`: still produces a valid (narrow) interval — this is why Wilson is better than Wald
- If `k == n`: ditto

**Why Wilson and not Wald (p ± z√(p(1-p)/n))**:
- Wald intervals can produce negative lower bounds or >1 upper bounds when accuracy is extreme
- Wilson intervals are always bounded in [0, 1]
- The brief explicitly says "confidence intervals on every metric, not point estimates" — Wilson is the standard for proportions

---

### 5.3 `walk_forward_accuracy(df, window_size=5) -> pd.DataFrame`

**Purpose**: Compute directional accuracy per walk-forward window with confidence intervals.

**Parameters**:
- `df`: `pd.DataFrame` — the loaded results DataFrame
- `window_size`: `int` — days per window. Default `5` per the brief.

**Returns**:
- `pd.DataFrame` with columns:
  - `window`: `str` — label like `"days_31-35"`
  - `n`: `int` — number of rows in this window
  - `correct`: `int` — number of correct predictions
  - `accuracy`: `float` — `correct / n`
  - `ci_low`: `float` — Wilson lower bound
  - `ci_high`: `float` — Wilson upper bound

**Algorithm**:
1. Extract unique days from the `day` column
2. Sort them ascending
3. Group into contiguous blocks of `window_size` days
4. For each block:
   - Filter `df` to rows where `day` is in the block
   - Count total rows `n`
   - Count rows where `predicted_direction == actual_direction`
   - Compute Wilson CI
5. Return as DataFrame

**Preconditions** (raises `ValueError` if missing):
- `df` must contain `day`, `predicted_direction`, and `actual_direction`

**Why contiguous blocks and not rolling overlap**:
- The brief says "5-day rolling blocks" — this is interpreted as contiguous, non-overlapping windows (31–35, 36–40, etc.)
- Overlapping windows would artificially inflate statistical power by reusing data
- Non-overlapping windows are independent enough for separate CI computation

---

### 5.4 `schema_pass_rate(df) -> (float, bool|None)`

**Purpose**: Compute the fraction of rows with valid JSON/schema output.

**Parameters**:
- `df`: `pd.DataFrame` — loaded results

**Returns**:
- `rate`: `float` — fraction in `[0.0, 1.0]`
- `passed`: `bool | None` — `True` if `rate >= min_schema_pass_rate`, `None` if threshold not yet set

**Implementation**:
- If `schema_valid` column exists: `rate = df["schema_valid"].mean()`
- If `schema_valid` is missing: infer from `reason_code` — `rate = (df["reason_code"] != "PARSE_FAILURE").mean()`

**Why this matters**:
- In production, invalid JSON causes downstream pipeline crashes
- The orchestrator's fallback (`NEUTRAL`, `conviction=0.0`) is the safety net, but a high parse-failure rate indicates the model itself is unreliable
- The brief calls this a liability, not a corner case

---

### 5.5 `conviction_calibration(df, n_bins=5) -> (pd.DataFrame, float, bool|None)`

**Purpose**: Compute Expected Calibration Error (ECE) and per-bin reliability data for the conviction field.

**Parameters**:
- `df`: `pd.DataFrame` — loaded results
- `n_bins`: `int` — number of conviction bins. Default `5`.

**Returns**:
- `bin_df`: `pd.DataFrame` — one row per bin with columns:
  - `bin`: `str` — label like `"0.00-0.20"`
  - `mean_conviction`: `float` — average conviction in bin
  - `actual_accuracy`: `float` — fraction of predictions in bin that were correct
  - `n`: `int` — number of samples in bin
  - `weight`: `float` — `n / total_samples`
- `ece`: `float` — Expected Calibration Error
- `passed`: `bool | None` — `True` if `ece <= max_ece`, `None` if threshold not set

**Algorithm**:
1. Create a `"correct"` column: `(predicted_direction == actual_direction).astype(int)`
2. Drop rows with missing `conviction`
3. Bin by `conviction` using `pd.cut(..., bins=n_bins, include_lowest=True)`
4. For each bin:
   - Compute `mean_conviction` = mean of conviction scores in bin
   - Compute `actual_accuracy` = mean of `"correct"` in bin
   - Compute `weight` = fraction of total samples in this bin
5. Compute `ECE = Σ (weight × |mean_conviction − actual_accuracy|)`

**Preconditions** (raises `ValueError` if missing):
- `df` must contain `conviction`, `predicted_direction`, `actual_direction`

**Edge Cases**:
- If a bin is empty, it is skipped (no contribution to ECE)
- If all rows have the same conviction, all but one bin will be empty — ECE may be `NaN` or `0.0`
- If `df` is empty after dropping NaNs, returns `(empty DataFrame, NaN, None)`

**Why ECE and not just a reliability plot**:
- The brief says: "not just a reliability diagram — explain what makes conviction a meaningful field"
- ECE compresses the entire reliability plot into a single interpretable number
- An ECE of 0.03 means conviction is well-calibrated; 0.25 means it is effectively random

**The Hard Design Problem**:
The model generates conviction as **text** (e.g., the string `"0.72"`), not as a softmax probability. The ECE measures whether your post-processing of that text (parsing, scaling, whatever you design) produces a meaningful score. If ECE is high, your conviction design failed — and the brief explicitly asks you to explain this in Section 3.

### 5.6 `orchestrator_rates(df) -> dict`

**Purpose**: Compute suppression, parse-failure, low-conviction downgrade, and pass rates.

**Parameters**:
- `df`: `pd.DataFrame` — loaded results

**Returns**:
- `dict` with keys:
  - `adx_suppressed`: `float` — fraction with `reason_code == "ADX_SUPPRESSED"`
  - `parse_failure`: `float` — fraction with `reason_code == "PARSE_FAILURE"`
  - `low_conviction`: `float` — fraction with `reason_code == "LOW_CONVICTION"`
  - `passed`: `float` — fraction with `reason_code == "PASSED"`
  - `n`: `int` — total number of samples

**No Thresholds**:
- The brief says "report honestly" for suppression rates
- 0% or 100% suppression is suspicious and should be investigated, but not automatically failing
- The purpose is diagnostic: which windows show elevated suppression and why?

**Diagnostic Value**:
- High `adx_suppressed` (e.g., >40%) → markets were mostly choppy during eval. Is this realistic? Did ADX behave as expected?
- High `parse_failure` (e.g., >5%) → the model is generating garbage. This is a training or architecture bug.
- High `low_conviction` (e.g., >30%) → the model is uncertain. Either the market was noisy, or conviction calibration is broken.

---

### 5.7 `regime_split(df, vix_col="vix") -> tuple`

**Purpose**: Split evaluation results by VIX regime and compare directional accuracy.

**Parameters**:
- `df`: `pd.DataFrame` — loaded results
- `vix_col`: `str` — column name for VIX. Default `"vix"`.

**Returns**:
- `high_vix_df`: `pd.DataFrame` — subset where `vix > median`
- `low_vix_df`: `pd.DataFrame` — subset where `vix <= median`
- `median_vix`: `float` — the median VIX value used for splitting
- `high_acc`: `float` — directional accuracy in high-VIX subset
- `low_acc`: `float` — directional accuracy in low-VIX subset
- `acc_diff`: `float` — `low_acc - high_acc`

**Algorithm**:
1. Compute `median_vix = df[vix_col].median()`
2. Split `df` into two subsets
3. If `predicted_direction` and `actual_direction` exist, compute accuracy for each subset
4. If either subset is empty, accuracy is `NaN`

**Preconditions** (raises `ValueError` if missing):
- `df` must contain the column specified by `vix_col`

**Why median split**:
- The brief says "high-VIX versus low-VIX regimes" but does not define the boundary
- Median split is the standard, data-driven approach — it guarantees equal sample sizes and avoids arbitrary thresholds
- Alternative: use the VIX regime table from the guide (<12, 12–16, 16–22, 22–30, >30). This is also defensible but splits are uneven.

**Threshold**:
- `min_high_vix_accuracy`: the minimum accuracy in high-VIX windows
- `max_vix_accuracy_gap`: the maximum allowed difference between low-VIX and high-VIX accuracy
- A model that works in calm markets but collapses under stress is dangerous

---

### 5.8 `run_full_eval(results_path) -> None`

**Purpose**: The master function. Loads results, computes all metrics, and prints a formatted report to stdout.

**Parameters**:
- `results_path`: `str` — path to `orchestrator_outputs.jsonl`

**Behaviour**:
1. Call `load_results(results_path)`
2. Call `walk_forward_accuracy(df)` → print table
3. Call `schema_pass_rate(df)` → print rate + pass/fail status
4. Call `conviction_calibration(df)` → print ECE + bin table + pass/fail status
5. Call `orchestrator_rates(df)` → print rates dict
6. Call `regime_split(df)` → print VIX split + accuracies
7. Call `missing_thresholds()` → warn if any thresholds are still unset

**Output Format**:

A structured text report with clear section headers, tables, and PASS/FAIL indicators. The output is designed to be copy-pasted directly into the report PDF (Section 4: Results).

## 6. How Results Are Generated (Upstream Pipeline)

The eval suite does not run in a vacuum. It depends on `src/run_eval.py` producing `orchestrator_outputs.jsonl`. Here is that flow:

### 6.1 `src/run_eval.py` Pipeline

```
1. Load market_states.parquet
2. Filter to eval window: df[df['day'] >= 31]
3. For each row:
   a. Extract market_state dict
   b. Build prompt (with or without RAG context)
   c. Call generate_signal(prompt) → raw model text
   d. Call run_orchestrator(market_state, model_fn) → parsed signal dict
   e. Append ground truth: actual_direction, vix, adx, day, timestamp
   f. Append to results list
4. Write results/orchestrator_outputs.jsonl
5. Call eval_suite.run_full_eval("results/orchestrator_outputs.jsonl")
```

### 6.2 The Two Conditions (RAG Ablation)

The RAG experiment requires running the full eval set **twice**:

- **Condition A (No RAG)**: `build_prompt_without_rag(market_state)` → standard prompt
- **Condition B (With RAG)**: `build_prompt_with_rag(market_state, k=3)` → prompt with 3 retrieved episodes

Each condition produces its own `orchestrator_outputs.jsonl` file:
- `results/orchestrator_outputs_no_rag.jsonl`
- `results/orchestrator_outputs_with_rag.jsonl`

The eval suite is run separately on each file. Results are compared in the report (Section 3: Fine-tuning and RAG).

### 6.3 Why This Separation Matters

- The eval suite is **pure analysis** — it knows nothing about models, prompts, or RAG
- The eval suite can be run on any `orchestrator_outputs.jsonl`, including synthetic test data
- This separation mirrors the brief's design: the orchestrator and eval are deterministic, model-agnostic layers

## 7. Threshold Research Guidelines

Before setting thresholds, consider:

### 7.1 Directional Accuracy Baseline
- Random guessing among 3 directions (`CE`, `PE`, `NEUTRAL`) = ~33% accuracy
- But the label distribution may not be uniform — check the training data
- Academic literature on NIFTY options ML: 52–55% directional accuracy is considered a modest but real edge
- **Recommendation**: Set `min_directional_accuracy` around 0.52, `fail_directional_accuracy` around 0.45

### 7.2 Schema Pass Rate
- In production, even 1% invalid JSON can crash downstream pipelines
- The orchestrator's fallback prevents crashes, but parse failures mean the model is misbehaving
- **Recommendation**: `min_schema_pass_rate` ≥ 0.97 (3% failure tolerance for a research artefact)

### 7.3 Conviction Calibration (ECE)
- ECE < 0.10 = well-calibrated
- ECE 0.10–0.20 = moderately calibrated
- ECE > 0.25 = poorly calibrated (conviction is not informative)
- **Recommendation**: `max_ece` = 0.15

### 7.4 High-VIX Robustness
- Markets are harder to predict when VIX is elevated (higher noise, regime shifts)
- A drop from 55% to 48% accuracy under stress is acceptable; a drop to 35% is not
- **Recommendation**: `min_high_vix_accuracy` = 0.48, `max_vix_accuracy_gap` = 0.10

### 7.5 Parse Failure Rate
- Any parse failure indicates the model output does not match the required schema
- **Recommendation**: `max_parse_failure_rate` = 0.03

## 10. Open Questions

These are decisions that must be made before implementation. They do not block scaffolding but must be resolved before the eval suite is committed.

1. **Conviction bin count**: Default is 5 bins. Is this granular enough given the model may output only a few discrete conviction values?
2. **Regime split method**: Median VIX split is standard. Should we also report fixed VIX regime splits (<16, 16–22, >22) for comparison?
3. **NEUTRAL prediction handling**: When `actual_direction == "NEUTRAL"`, a `predicted_direction == "NEUTRAL"` is "correct." Should NEUTRAL predictions be excluded from directional accuracy to focus only on CE/PE edge detection? The brief is ambiguous here.
4. **RAG ablation comparison**: Should the eval suite include a function to directly compare two result files (no-RAG vs with-RAG), or should this be done manually in the report?
